# 出差费用报销申请表

升级后建议新开会话；继续当前会话时重新加载新版入口和本流程说明。草稿按[24小时复用与刷新](../../../references/WORKFLOW-DIRECTORY.md#办理行为)：首个可核对草稿起24小时，编辑不续期、提交不全量重查；过期或用户要求用 `refresh <draftId>`，保留输入、材料和回执，展示并确认实际差异。

本 Skill 办理出差费用报销，workflow key 为 `trip_expense_reimbursement`，固定目标为 `FORM-FF467D1C65F940C2A7A65C6EA234BB95QVO8`。出差申请使用[正式出差](../../business/business-trip-application/SKILL.md)，一般费用报销使用[费用报销](../expense-reimbursement/SKILL.md)。

优先遵守[公司维护源与个人选择](../../../references/FINANCE-DETAILS.md#公司维护源与个人选择)：汇率、币种、科目目录及差旅津贴标准按公司来源，口述、网络或 personal 不覆盖。项目科目可由员工合法改选，普通出差固定科目保持；差旅津贴允许的本次调整按下述规则保留。

从本文件向上三级确定完整包根。首次使用按[入口 Skill](../../../SKILL.md#首次安装)准备官方 OpenYida CLI；以后复用官方登录态，仅在脚本要求时引导本人完成官方登录。

```text
node scripts/fargowork.cjs status
node scripts/fargowork.cjs requirements trip_expense_reimbursement
node scripts/fargowork.cjs details trip_expense_reimbursement --input <绝对路径UTF-8明细JSON>
```

语义输入文件由 Agent 维护，不要求员工编辑 JSON、查内部编号或编写程序。按既定编排直接办理，仅缺失、冲突或失败时定向排查；日常只展示必要业务问题、明细、完整申请和结果。

## 先整理行程与明细

只处理员工本次提供的材料，优先使用宿主已有 PDF、图片、OCR 和表格能力；可读就不重复解析或另装指定工具。同一费用的发票、订单、付款截图合为证据，不重复计额。保留员工已修正、排除和拆分的结果，不从“$”猜币种，不把材料中所有数字相加。

票据姓名与报销人不同只提示一次，让员工选按当前报销人继续、更换报销人或由本人切换账号；已解释或明确继续后不反复追问，不猜业务关系、不要求HR新增人员。发起人与报销人不同可按既有白名单代办规则处理。

1. 默认报销人为当前登录人。员工明确要求代办时，以 `claimant_query` 按姓名查官方候选；仅获准的登录人员可选择其他报销人，将员工明确选中的候选写入 `claimant_user_id`。同名先选择，不逐个读花名册，不猜人员 ID。草稿归属和实际提交者仍是当前登录人，预览明确显示本次报销人。
2. 按行整理 `items`。行程使用 `departure`、`destination`、`region`、`start_date`、`end_date`；日期按 `YYYY-MM-DD`，区域从脚本返回的合法选项选择。实报费用分为 `airfare`、`accommodation`、`local_transport`、`other_expenses`，币种使用 `original_currency`，说明用 `remarks`。原表可空项保持可空，不为凑齐表格补零、补日期或新增门禁。
3. 确定报销人后，即使尚无 `items` 也先用只读 `details` 解析其支付公司和收款币种，再换汇及计算差旅津贴。唯一合法候选直接采用并告知；多个候选从返回选项填写 `payment_company`、`reimbursement_currency`，集中请员工选择。查询为空请财务核查维护记录、权限及匹配条件，不能断言未维护。银行、申请部门及无关主表资料留到明细确认之后。
4. **在明细计算及科目推荐前明确是否项目。** 用户已明确说明的沿用；尚未明确时集中询问“是否属于项目？如是，属于哪个项目？”，可以与必要行程问题合并。不得因未提项目、内部协作、历史习惯或关联出差单存在而自行填写 `is_project: false`。项目报销沿本流程输入 `is_project: true`、`project_name`、`project_expense_category`，各行使用 `project_department_name`、业务层级及 `account`。Agent结合用途和合法配对给出一组建议，写入 `account` 和简短 `classification_reason` 后再校验。完整草稿也读取 `recommendationContexts`，按[科目推荐与独立备选](../../../references/FINANCE-DETAILS.md#科目推荐与独立备选)在明细外提供少量合理备选，不混写字段、不覆盖合法明确选择。备选限当前项目类别，显式改共同类别时核对全部受影响行。普通报销固定科目保持，不开放选择，保留出差本身字段与独立块结构。
5. 关联出差使用每行 `trip_instance_id`，从脚本返回且申请人属于本次报销人、已结束且审批通过的候选中选择。用行程和日期帮助辨认，不能只凭相同名称猜单。只有脚本确认适用原表例外时才可不关联；例外仅免必填，不改变已选择关联单的范围检查。
6. 差旅津贴按区域、真实日期和公司标准由代码建议：**收款CNY用CNY津贴，其他收款币种（含HKD、SGD、USD）用HKD津贴**。按实际行程顺序每行首尾均计，只计算前面所有行未覆盖的日期，重叠日归前段并用前段标准；支持一单多次独立出差和同段多币种拆行，后面的重复日期不再自动计额。真实日期不改，分别展示行程天数、津贴建议天数及分配说明。未主动调整时不传 `allowance_amount` 当手工覆盖；员工明确修改的值（含0或清空）持续保留，不以自动建议覆盖。日期或行程顺序不清楚就直接问员工，不从住宿发票猜日期。

实报金额、汇率、逐行换算和合计由工具按原表规则计算，不手填汇率或计算结果。差旅津贴与实报分别核对币种和金额，不混币相加；目录或汇率缺失按提示核查，不猜市场值。津贴仅用CNY或HKD，不限制合法报销币种或费用原币种；津贴折港币按津贴自身币种取公司维护汇率。

## 可修改明细与第一次确认

```text
node scripts/fargowork.cjs review trip_expense_reimbursement --input <绝对路径UTF-8明细JSON>
node scripts/fargowork.cjs review trip_expense_reimbursement --draft <draftId> --input <绝对路径UTF-8明细JSON>
```

用 `review` 保存当前明细及材料范围，**默认呈现返回的 `detailEditor.url`（不可用时打开 `detailEditor.path` 的Markdown） 对应 HTML，不等待用户提醒，保存直接写回本机草稿**。按[明细编辑与回读](../../../references/FINANCE-DETAIL-EDITOR.md)打开本机页面。固定为**每条明细独立一块**，每块放齐行程／完整日期、**本行关联出差**、四项实报费用、原币种、报销金额、差旅津贴币种／标准／建议天数／金额／分配说明、项目归属和备注；不拆成不同表分散核对。标题及合计由代码生成，不另编表格、不展示汇率。首版显示项目／非项目、项目名，未知标待补；币种及分项合计分明，可空项保留空。“飞机、车船票款”含火车票，“其他费用”可含退票费，解释放备注，不自拆列。材料格式见[财务明细](../../../references/FINANCE-DETAILS.md#出差费用报销)。明细前醒目提示“**只需修改明细，无需自己计算总额。保存后告诉 Agent‘改好了’，报销金额和总额会重新计算。**”

员工可口述修改，Agent 回写同一草稿 `review`；也可在HTML中点击保存（兜底时编辑原Markdown并保存），告知“改好了”后执行 `read-edit <draftId>`。代码识别变化、保留其他手改及材料关系，重算后更新同一草稿及页面，只简短回显受影响行与合计。汇率及派生金额不从 HTML 导入，24小时内复用已有公司汇率；明确手改津贴金额（含0或清空）持续保留，不以建议覆盖。无需导出、上传或截图，保存／应用不代替确认。`items` 显式传入替换整表，不能只传改动行；增删行同步材料对应。省略 `materials` 沿用，`[]` 才清空，未处理材料保持待核。

`needsInput` 的 Agent 推荐项先由 Agent 处理；员工能回答的疑问集中补问。缺项未解决时可以保存和展示待补 HTML，不能声称已核对或进行确认。明细完整后展示当前 HTML、材料范围及合理备选，**停止并等待员工的新答复**。接受推荐即可确认；明确替换已展示的项目科目且其余保持时，回写并重新 `review`，核对只有指定变更、金额／材料／共同类别及其他行无额外变化，展示更新后的 HTML 并简短回显后用新的摘要继续，不重问未改行。额外变化仍展示并取得确认。随后执行：

```text
node scripts/fargowork.cjs confirm-details <draftId> --confirm <本次reviewSha256>
```

编辑、保存和最初的办理意图都不等于确认。第一次确认只允许继续补齐申请，不授权提交。

## 补主表与最终确认

1. 在同一草稿调用 `prepare trip_expense_reimbursement --draft <draftId> --input <绝对路径UTF-8业务JSON>`；省略 `items` 沿用当前明细。收款资料先从本次报销人花名册带入，允许修改或明确清空：`bank_account`、`bank_name`、`bank_city`、`bank_branch`、`account_name`。账号保持字符串，保留前导零和全部数字；来源无法保持原文时补充本次准确账号，不能从数值猜回。
   本人明确要求本次换卡时，按[本次换收款卡](../../../references/PERSONAL.md#本次换收款卡)在同一草稿检索本人遮掩历史候选，或自行提供；选定后整组替换五项并保留最终确认。代办不查询对方历史卡，使用其花名册或明确的本次资料。
2. 申请部门限定本次报销人任职部门。多部门、支付公司或业务线候选需要选择，唯一合法候选可以采用并纳入业务预览；支付/承担公司及业务层级沿本流程 `requirements` 和返回的候选补齐。正常隐藏的主管、财务、出纳、内部身份和后台计算不让员工核对。
3. `attachments` 使用本地绝对路径，至少1件、最多20件、单件100 MiB；格式由脚本按当前 Schema 检查，见[附件规则](../../../references/ATTACHMENTS.md)。从已确认纳入（`included`）的材料范围选择最终附件，排除、重复或无关材料不随原始整批自动上传；未决材料先核对范围。合规文件直接使用，转换或合并时保留原件及费用对应关系，但不默认同时上传合并件和全部原件，不因合并文件减少费用行，不改变票面金额或静默丢材料。
4. 同一草稿保留已知上传结果；上传未知时核查，不自动重传。明细、报销人、关联单、差旅津贴币种或材料范围变化后核对并确认受影响明细；仅改银行等无关主表内容保留首轮确认，仍须更新最终预览。

准备完成后执行 `preview <draftId>`，呈现本次完整申请 HTML：报销人、申请部门、公司、项目归属、收款资料、全部行程费用、差旅津贴与实报币种／合计、关联出差及附件名，说明首轮后的变化。汇率仍不展示；主表编辑回到同一草稿，本地重算后更新同一草稿及页面。**展示后停止，等待针对完整申请的新提交确认。** 明细确认、选人、选关联或最初“帮我提交”不代替本次答复。

收到新确认后，仅执行一次 `submit <draftId> --confirm <本次preview返回的draftSha256>`。不要把准备、预览、提交串成一次执行。成功简短报告提交结果和编号，不代表审批通过；未知结果用同一草稿 `result <draftId>` 核查，不能重起草稿重提。提交状态与内容回读核验分别报告。

本次报销人为当前本人且本次补录或修改了收款资料时，按[默认银行卡约定](../../../SKILL.md#财务与资料规则)先完成本次申请。成功后、员工未说明是否长期使用时才可选问一次是否另办默认变更；已说“仅本次”就不再问，不自动创建第二单。代办不自动引出对方的默认资料变更。

只使用本包固定业务入口。真正阻断时按[资料检查](../../../references/CHECKS.md)和[DEBUG](../../../references/DEBUG.md)处理，不索取凭据、不更换目标或扩大查询范围。
