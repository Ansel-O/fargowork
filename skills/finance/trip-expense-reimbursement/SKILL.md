# 出差费用报销申请表

本 Skill 办理出差费用报销，workflow key 为 `trip_expense_reimbursement`，固定目标为 `FORM-FF467D1C65F940C2A7A65C6EA234BB95QVO8`。出差申请使用[正式出差](../../business/business-trip-application/SKILL.md)，一般费用报销使用[费用报销](../expense-reimbursement/SKILL.md)。

优先遵守[公司维护源与个人选择](../../../references/FINANCE-DETAILS.md#公司维护源与个人选择)：汇率、币种、科目目录及餐补标准按公司来源，口述、网络或 personal 不覆盖。项目科目可由员工合法改选，普通出差固定科目保持；餐补明确允许的本次调整仍按下述规则保留。

从本文件向上三级确定完整包根。首次使用按[入口 Skill](../../../SKILL.md#首次安装)准备官方 OpenYida CLI；以后复用官方登录态，仅在脚本要求时引导本人完成官方登录。

```text
node scripts/fargowork.cjs status
node scripts/fargowork.cjs requirements trip_expense_reimbursement
node scripts/fargowork.cjs details trip_expense_reimbursement --input <绝对路径UTF-8明细JSON>
```

语义输入文件由 Agent 维护，不要求员工编辑 JSON、查内部编号或编写程序。日常只展示必要业务问题、明细、完整申请和结果。

## 先整理行程与明细

只处理员工本次提供的材料，优先使用宿主已有 PDF、图片、OCR 和表格能力；可读就不重复解析或另装指定工具。同一费用的发票、订单、付款截图合为证据，不重复计额。保留员工已修正、排除和拆分的结果，不从“$”猜币种，不把材料中所有数字相加。

1. 默认报销人为当前登录人。员工明确要求代办时，以 `claimant_query` 按姓名查官方候选；仅获准的登录人员可选择其他报销人，将员工明确选中的候选写入 `claimant_user_id`。同名先选择，不逐个读花名册，不猜人员 ID。草稿归属和实际提交者仍是当前登录人，预览明确显示本次报销人。
2. 按行整理 `items`。行程使用 `departure`、`destination`、`region`、`start_date`、`end_date`；日期按 `YYYY-MM-DD`，区域从脚本返回的合法选项选择。实报费用分为 `airfare`、`accommodation`、`local_transport`、`other_expenses`，币种使用 `original_currency`，说明用 `remarks`。原表可空项保持可空，不为凑齐表格补零、补日期或新增门禁。
3. 确定报销人后，即使尚无 `items` 也先用只读 `details` 解析该报销人的支付公司和收款币种，再开始换汇及餐补计算。唯一合法候选直接采用并告知；多个候选时从返回选项填写 `payment_company`、`reimbursement_currency`，集中请员工选择。查询为空请财务核查维护记录、查看权限及匹配条件，不能断言未维护。银行、申请部门及无关主表资料留到明细确认之后。
4. **在明细计算及科目推荐前明确是否项目。** 用户已明确说明的沿用；尚未明确时集中询问“是否属于项目？如是，属于哪个项目？”，可以与必要行程问题合并。不得因未提项目、内部协作、历史习惯或关联出差单存在而自行填写 `is_project: false`。项目报销沿本流程输入 `is_project: true`、`project_name`、`project_expense_category`，各行使用 `project_department_name`、业务层级及 `account`。Agent结合用途和合法配对给出一组建议，写入 `account` 和简短 `classification_reason` 后再校验。完整草稿也读取 `recommendationContexts`，按[科目推荐与独立备选](../../../references/FINANCE-DETAILS.md#科目推荐与独立备选)在表外按行同时说明合理备选及理由，不混写字段、不覆盖合法明确选择。备选限当前项目类别，显式改共同类别时核对全部受影响行。普通报销固定科目保持，不开放选择，也不套费用报销八列。
5. 关联出差使用每行 `trip_instance_id`，从脚本返回且申请人属于本次报销人、已结束且审批通过的候选中选择。用行程和日期帮助辨认，不能只凭相同名称猜单。只有脚本确认适用原表例外时才可不关联；例外仅免必填，不改变已选择关联单的范围检查。
6. 餐补按区域、实际行程日期和公司维护标准由工具给建议：**收款币种为CNY时餐补为CNY，其余收款币种（含HKD、SGD、USD）餐补均为HKD**；票据原币种只用于实报费用换算。同一自然日只自动计一次，首尾均计、单日为一天；跨城当天归到达的下一段，按该段地区标准。真实起止日期保持原样，分别展示行程天数和餐补建议天数，工具返回的共享日分配说明放在表外。同一天连续转场时按已明确的行程先后整理各段。同段多币种拆行只建议一次，其余相关行默认0。员工明确修改的 `allowance_amount`（包括0或清空）保持，不以重算覆盖。日期、城市到达/离开或先后不清楚时直接集中询问，不从住宿发票推定晚数，不长时间猜测。

实报金额、汇率、逐行换算和合计由工具按原表规则计算，不手填汇率或计算结果。餐补与实报分别核对币种和金额，不能把不同币种直接相加；目录或汇率确实缺失时按返回提示检查资料，不猜市场汇率。餐补仅使用CNY或HKD，不限制公司目录允许的报销币种和费用原币种；餐补折港币时按餐补自身币种取公司维护汇率。

## 可修改明细与第一次确认

```text
node scripts/fargowork.cjs review trip_expense_reimbursement --input <绝对路径UTF-8明细JSON>
node scripts/fargowork.cjs review trip_expense_reimbursement --draft <draftId> --input <绝对路径UTF-8明细JSON>
```

用 `review` 保存当前明细及材料范围，**默认打开返回的 `detailEditor.path` 展示出差 HTML 明细，不等待用户要求**。按[HTML 明细与修改](../../../references/FINANCE-DETAIL-EDITOR.md)办理；宿主不能内嵌时提供本地 HTML 链接供浏览器打开。页面保留出差自己的列：行程、日期、**每行自己的关联出差流程**、各项实报、原币种与换算、餐补和备注，以及实际需要的项目归属。首版即展示“项目／非项目”和项目名称；未确定时明确待补。明确标出实报及餐补币种，展示分项合计；可空列允许留空。保持工具返回的原列名称和顺序：“飞机、车船票款”包含火车票，“其他费用”可包含退票费，解释写备注或表外，不自行拆列或改名。材料范围格式见[财务明细](../../../references/FINANCE-DETAILS.md#出差费用报销)。

允许员工直接说出修改，也可在 HTML 增删改行、拆币、排除材料、纠正识别和调整餐补。口述修改回写同一草稿并重新 `review`；手动修改由员工导出文件交 Agent 执行 `apply-edit`。两种方式都展示工具新返回的 `detailEditor.path`，说明受影响行及更新合计，保留其他手改；手动应用后等待用户对新版的明确确认，导出或应用不代替确认。`items` 显式传入时替换整表，不能只传改动行；增删行后同步更新材料对应关系。省略 `materials` 沿用材料范围，显式 `[]` 才清空。未处理清楚的材料应保留待核，不能静默忽略。

`needsInput` 的 Agent 推荐项先由 Agent 处理；员工能回答的疑问集中补问。缺项未解决时可以保存和展示待补 HTML，不能声称已核对或进行确认。明细完整后展示当前 HTML、材料范围及合理备选，**停止并等待员工的新答复**。接受推荐即可确认；明确替换已展示的项目科目且其余保持时，回写并重新 `review`，核对只有指定变更、金额／材料／共同类别及其他行无额外变化，展示新版 HTML 并简短回显后用新的摘要继续，不重问未改行。额外变化仍展示并取得确认。随后执行：

```text
node scripts/fargowork.cjs confirm-details <draftId> --confirm <本次reviewSha256>
```

编辑、保存和最初的办理意图都不等于确认。第一次确认只允许继续补齐申请，不授权提交。

## 补主表与最终确认

1. 在同一草稿调用 `prepare trip_expense_reimbursement --draft <draftId> --input <绝对路径UTF-8业务JSON>`；省略 `items` 沿用当前明细。收款资料先从本次报销人花名册带入，允许修改或明确清空：`bank_account`、`bank_name`、`bank_city`、`bank_branch`、`account_name`。账号保持字符串，保留前导零和全部数字；来源无法保持原文时补充本次准确账号，不能从数值猜回。
   本人明确要求本次换卡时，按[本次换收款卡](../../../references/PERSONAL.md#本次换收款卡)在同一草稿检索本人遮掩历史候选，或自行提供；选定后整组替换五项并保留最终确认。代办不查询对方历史卡，使用其花名册或明确的本次资料。
2. 申请部门限定本次报销人任职部门。多部门、支付公司或业务线候选需要选择，唯一合法候选可以采用并纳入业务预览；支付/承担公司及业务层级沿本流程 `requirements` 和返回的候选补齐。正常隐藏的主管、财务、出纳、内部身份和后台计算不让员工核对。
3. `attachments` 使用本地绝对路径，至少1件、最多20件、单件100 MiB；格式由脚本按当前 Schema 检查，见[附件规则](../../../references/ATTACHMENTS.md)。从已确认纳入（`included`）的材料范围选择最终附件，排除、重复或无关材料不随原始整批自动上传；未决材料先核对范围。合规文件直接使用，转换或合并时保留原件及费用对应关系，但不默认同时上传合并件和全部原件，不因合并文件减少费用行，不改变票面金额或静默丢材料。
4. 同一草稿保留已知上传结果；上传未知时核查，不自动重传。明细、真实报销人、关联单、餐补币种或材料范围变化后重新核对并确认受影响明细；仅改银行等无关主表内容可保留首轮确认，但必须更新最终预览。

准备完成后执行 `preview <draftId>`，打开本次 `detailEditor.path` 展示完整申请 HTML：报销人、申请部门、公司、业务/项目归属、完整收款资料、全部行程费用、餐补与实报币种/合计、关联出差及最终附件名称，说明首轮之后的业务变化。主表口述或手动修改也回到同一草稿，重算后展示新版 HTML。**展示后停止，等待员工下一条针对完整申请的新提交确认。** 第一次明细确认、选人、选关联单或最初“帮我提交”不能代替本次答复。

收到新确认后，仅执行一次 `submit <draftId> --confirm <本次preview返回的draftSha256>`。不要把准备、预览、提交串成一次执行。成功简短报告提交结果和编号，不代表审批通过；未知结果用同一草稿 `result <draftId>` 核查，不能重起草稿重提。提交状态与内容回读核验分别报告。

本次报销人为当前本人且本次补录或修改了收款资料时，按[默认银行卡约定](../../../SKILL.md#财务与资料规则)先完成本次申请。成功后、员工未说明是否长期使用时才可选问一次是否另办默认变更；已说“仅本次”就不再问，不自动创建第二单。代办不自动引出对方的默认资料变更。

只使用本包固定业务入口。真正阻断时按[资料检查](../../../references/CHECKS.md)和[DEBUG](../../../references/DEBUG.md)处理，不索取凭据、不更换目标或扩大查询范围。
