# 费用报销申请表

升级后建议新开会话；继续当前会话时重新加载新版入口和本流程说明。草稿按[24小时复用与刷新](../../../references/WORKFLOW-DIRECTORY.md#办理行为)：首个可核对草稿起24小时，编辑不续期、提交不全量重查；过期或用户要求用 `refresh <draftId>`，保留输入、材料和回执，展示并确认实际差异。

本 Skill 办理费用报销，固定目标为 `FORM-6EB2E57A94CF4445BB28508DC45262E3MDDX`，workflow key 为 `expense_reimbursement`。不能当作出差报销、对外付款或餐费补贴的替代入口。

办理时优先遵守[公司维护源与个人选择](../../../references/FINANCE-DETAILS.md#公司维护源与个人选择)：汇率及合法目录按公司来源核对，用户口述、网络或 personal 不能覆盖；类别／科目仍由员工在合法范围内接受或改选，财务按原流程审核。

从本文件向上三级确定完整包根。首次使用按[入口 Skill](../../../SKILL.md#首次安装)准备官方 OpenYida CLI 并安装本包；以后复用官方登录态，不注册 MCP。

```text
node scripts/fargowork.cjs status
node scripts/fargowork.cjs requirements expense_reimbursement
node scripts/fargowork.cjs details expense_reimbursement --input <绝对路径的UTF-8明细JSON>
```

仅在 `status` 要求登录时引导本人完成官方登录。以下语义输入文件由 Agent 维护，不要求员工编辑 JSON、注册 MCP 或编写调用程序。按既定命令直接办理，仅缺失、冲突或执行失败时定向排查；合并询问员工能回答的缺项，不输出逐步技术报告。

## 先整理并确认明细

先用 `details` 查询本人支付公司和收款币种，尚无 `items` 也可调用。唯一合法组合直接采用并告知；多个公司或币种时集中让员工选择，分别填 `payment_company`、`reimbursement_currency`，历史习惯只作建议。没有有效结果时，请财务核查维护记录、查看权限和匹配条件，不断言未维护或要求新增。币种未定先保留材料事实，不计算完整报销明细。

在推荐类别／科目前明确 `is_project`：员工已说明则沿用；未说明就问“这笔费用是否属于项目？如是，属于哪个项目？”。不能因未提项目、内部协作或旧习惯自行填 `false`。项目从合法目录选 `project_name`、`project_expense_category`；项目名和共同类别在明细顶部只显示一次，各行仍核对项目科目。项目部门和业务层级沿现有字段与合法候选，在对话收集必要选择，不搬到明细页面，也不套用出差的整单项目业务字段。

仅整理员工本次提供的材料，不自动搜索邮箱、聊天或历史报销补材料。优先用员工或宿主已有的 PDF、图片、OCR 和表格能力，能读清就不重复解析或另装同类工具。本包接收整理后的费用事实，展示和手动修改使用[统一明细模板](../../../references/FINANCE-DETAIL-EDITOR.md)。

默认一笔实际费用一行；同笔费用的发票、订单和付款截图合为证据，一张付款单包含多笔费用时可以拆行。区分本次实付金额、套餐标价、折扣和退款；总额已含税时不重复加税。数字、币种或费用归属确实含糊才集中补问，不能从“$”自行猜币种。保留员工纠错、排除和拆分结果，后续重读不得覆盖。

按[财务明细工具](../../../references/FINANCE-DETAILS.md)执行以下顺序：

1. 支付公司、收款币种和是否项目明确后，已解析内容写入 `items[].description`，原币金额、币种分别写入 `amount`、`original_currency`。用只读 `details` 取得实际科目候选和换算信息；此时不传 `attachments`，不要求员工先补银行、部门和全部业务线。项目报销使用 `is_project: true`；员工明确非项目时填 `false`，不填其他项目字段。
2. **Agent 根据每行实际用途，从返回的合法类别与科目完整配对中建议一组，写入 `expense_category`、`account` 和一句 `classification_reason`，再运行 `details`。** 完整合法草稿也读取 `recommendationContexts`；按[科目推荐与独立备选](../../../references/FINANCE-DETAILS.md#科目推荐与独立备选)为该行筛选1至2个合理备选，无合适备选就不凑数。展示元数据在 `review` 输入的 `recommendations` 中按首选、备选顺序提供（包含首选本身）：每项用 `rowNumber`（从1起）、与该行完全相同的 `description`、合法 `category`／`account` 及一句 `reason`（最多300字），示例见[编辑说明](../../../references/FINANCE-DETAIL-EDITOR.md#五份-md-固定模板)。它不传给只读 `details`，也不混入实际 `items[].account`。类别／科目保留完整原文，不编置信百分比；员工可展开当前类别全部合法科目。已有合法明确选择保持，不用样例中的用途或科目编号套本次申请。`resolver: agent_recommendation` 由 Agent 处理，用途不足或明确选择冲突时补问业务事实。
3. 汇率由工具按原币种和支付公司的报销币种查维护表并计算。唯一支付公司直接使用；多家公司确需员工选择时才问。不要要求员工手填已有汇率，也不自行使用市场汇率替代。
4. 用 `review expense_reimbursement --input <明细文件>` 保存首轮草稿，后续修改加 `--draft <同一draftId>`。**默认打开返回的 `detailEditor.url`，展示费用报销专用紧凑七列HTML，不等待用户提醒。** 页面保存直接写回同草稿原MD；本机页面不可访问时才打开 `detailEditor.path` 的原Markdown兜底。七列为**费用类别、会计科目、内容详情、原币金额、原币种、报销金额、备注**；类别／科目完整原文不缩写，原币种和换算报销金额只读，类别、科目、内容、原币金额及备注按合法范围修改。项目类别为整单共用值，只在顶部核对，行内使用项目科目，不能各行独立改类别。银行、部门、业务层级、汇率和后台计算不进入明细；需改原币种或项目归属时口述处理。标明报销币种、各原币小计和报销合计。每行科目只给默认建议的一句理由、1至2个合理备选和展开当前类别全部合法科目的入口，不加长篇说明。明细前醒目提示“**只需修改明细，无需自己计算总额。保存后告诉 Agent‘改好了’，报销金额和总额会重新计算。**”
5. 员工可口述修改明细，Agent 回写同一草稿后 `review`；也可在HTML中点击保存（兜底时编辑原Markdown并保存），告知“改好了”后调用 `read-edit <draftId>` 回读。使用[明细编辑与回读](../../../references/FINANCE-DETAIL-EDITOR.md)保留材料关系、未改内容和行身份，两种方式共用代码重算并更新同一草稿及明细页面。汇率和派生金额不从 HTML 导入，只复用已有公司汇率；不让员工导出、上传或发截图。简短回显受影响行和新合计，保存／应用不代替确认；待补 HTML 缺项未解不能确认。
6. 明细完整且 `needsInput` 已解决时，展示当前 HTML、材料范围及候选，**停止并等待员工的新答复**。接受推荐即可确认；明确替换已展示的某行且其余保持时，回写并重新 `review`，核对只有员工指定的变更、没有新金额／材料／共同类别连带变化，展示更新后的 HTML 并简短回显后用新 `reviewSha256` 执行 `confirm-details`，继续补主表，不重问未改行。额外变化仍展示并取得确认。仅编辑、保存或最初“帮我报销”不等于确认；第一次明细确认也不授权提交。

## 补齐申请资料

1. 在已确认明细的同一草稿运行 `prepare expense_reimbursement --draft <draftId> --input <业务文件>`。省略 `items` 沿用当前明细；显式传入 `items` 表示替换整张明细表，不能只传改动行。明细1至50行，备注可空，顶层说明用 `description`。金额按原表精确到两位小数，不额外添加正数限制。
2. 查询本人的必要资料。支付公司来自本人稳定 userid 的映射，不用任意公司代替。收款资料首次从本人花名册带入，允许修改或清空：`bank_account`、`bank_name`、`bank_city`、`bank_branch`、`account_name`。账号必须是字符串，保留前导零及全部数字，不转成数字或科学计数法；来源账号若无法保持原文，需员工补充。脚本保留同一草稿中已修改或清空的收款资料，不以花名册刷新覆盖。
3. 沿用首轮确定的支付公司、收款币种及项目，不重复询问。多个本人任职部门或业务线候选时，让员工选择，不静默选第一项。部门可传 `department_name`，脚本返回候选后对应填写 `department_id`，二者同时填写须一致。按返回层级确定 `business_structure`、`business_line`、`business_subline`；唯一候选直接采用并纳入预览。报销币种只可从该支付公司的维护候选中选择，不接受手填汇率或计算结果。
4. `same_bearing_company` 默认 `true`；由另一公司承担时设为 `false`，再从合法候选中选 `bearing_company`。已有明确输入不能静默替换。
5. 普通报销各行使用 `expense_category`、`account`。项目报销沿用明细前已确定的 `is_project: true`、`project_name`、`project_expense_category`，各行的 `project_department_name`、业务层级及 `account` 仍按原流程字段保存，项目部门可以逐行不同、候选限所选项目。这些必要选择在对话中补齐，页面不新增部门或业务层级控件；不因展示调整迁移原生字段、不套出差整单项目三层、不用普通费用类别覆盖项目主表类别。
6. 复用已确认类别、科目和 `classification_reason`，不从头问。`prepare` 在24小时内复用目录及来源，只补取尚缺的主表资料；不因补主表全量重查。主动刷新或新选择带来实际明细变化时，展示受影响行并确认，不能自动接受新金额。理由最多300字符，只用于预览，不写表单；合法显式选择保留，冲突先澄清。
7. 每行先按配置汇率从原币换算到报销币种，再由脚本计算后台所需金额。合计使用每行已舍入的报销额；不能由 Agent 自算总额覆盖脚本。公司、项目或业务归属变化后重新准备，复查依赖项。

收款账号、账户名称按原表必填；其他可空资料不额外设置门禁。部门主管、财务、出纳及内部计算等隐藏资料正常时不展示、不确认。原表的付款状态、实际付款日期属于后续节点，不在发起时填写。确实阻断办理时按[资料检查](../../../references/CHECKS.md)引导联系 HR、Finance 或 IT。

本人没有默认收款资料或指定本次换卡时，按其已明确的资料继续当前报销，将实际收款资料纳入最终完整申请预览；不单独重复确认已明确的修改，也不提前引导变更流程。只有员工主动单独要求先改默认资料时，才保留当前报销草稿并转入[默认银行卡变更申请](../default-bank-change/SKILL.md)。

员工明确要求本次换卡时，按[本次换收款卡](../../../references/PERSONAL.md#本次换收款卡)在同一草稿检索本人遮掩历史候选，或自行提供；选定后整组替换五项，再纳入最终申请确认。默认仍取花名册，不因 personal 偏好自动查卡。

## 附件与最终确认

最终文件使用顶层 `attachments: [本地绝对文件路径]`，至少一件、最多20件、单件100 MiB；支持格式由脚本核对当前表单。完整方法见[附件规则](../../../references/ATTACHMENTS.md)。只上传本次材料及必要转换件，使用宜搭原生附件。

文件不符合格式、数量或大小时，优先复用已有文件工具转换或合并，保留原件和费用对应关系；符合条件的文件直接使用。处理不得改变费用金额或静默排除材料，不能生成新费用。无法处理时说明受影响的文件，让员工补充可读副本或决定本次范围；没有页码、OCR 坐标或置信度不是新增门禁。

补充或修订持续使用同一 `draftId`。同一草稿复用已知上传；上传结果未知时停止核查，不自动重传。明细、证据范围或报销币种发生变化，先重新核对并确认受影响明细；只改收款资料等不影响明细的主表内容，保留明细确认，但需更新最终预览。

准备完成后调用 `preview <draftId>`，**在对话中核对完整申请，不生成整单HTML或主表编辑页**：本人部门、支付和承担公司、业务归属、实际完整收款资料、已确认明细及报销总额、附件名称。汇率仍不展示，简短说明首轮之后的变化。主表修改在同一草稿用 `prepare` 后更新对话预览；明细修改回同草稿 `review`，保存回读和明细确认按原规则处理。原明细页继续保留，不因进入主表阶段变成整张申请表。**展示后停止，等待员工下一条针对完整申请的明确提交确认。** 首次明细确认、最初“帮我报销”“提交吧”或选择某项候选，都不能代替这次确认。

收到新确认后执行 `node scripts/fargowork.cjs submit <draftId> --confirm <本次preview返回的draftSha256>` 一次，不能将准备、预览、提交串成一次执行。修改后展示本地重算结果；过期用 `refresh <draftId>`，账号变化不能沿用原账号草稿。成功简短报告结果和编号，不代表审批通过。未知结果用 `result` 核查，不重提；回读与提交状态分开报告。

本次报销提交成功后，仅在补录或修改了收款资料、且员工未说明是否长期使用时，简短问一次是否另提[默认银行卡变更申请](../default-bank-change/SKILL.md)。已说“就这一次／仅本次”的不再询问。这是可选后续，不自动创建或提交第二单，不改写花名册；愿意办理后仍需独立展示变更预览并取得新确认。变更申请提交成功不代表默认资料已经生效。

只使用本包固定业务命令，不检索其他表单、不临时编写 HTTP 调用或修改连接器扩大查询范围。排障按[DEBUG](../../../references/DEBUG.md)，不索取凭据。
