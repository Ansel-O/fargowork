# 默认银行卡变更申请

升级后建议新开会话；继续当前会话时重新加载新版入口和本流程说明。草稿按[24小时复用与刷新](../../../references/WORKFLOW-DIRECTORY.md#办理行为)：首个可核对草稿起24小时，编辑不续期、提交不全量重查；过期或用户要求用 `refresh <draftId>`，保留输入、材料和回执，展示并确认实际差异。

本 Skill 使用 `default_bank_change`，固定目标为 `FORM-119A5B3BC5034DFEB609977A41F2EBE576IB`。办理本人默认收款资料变更，适用于原来没有银行卡信息或希望换卡的员工。

按[公司维护源与个人选择](../../../references/FINANCE-DETAILS.md#公司维护源与个人选择)区分本次合法输入与公司规则：员工可明确提供新的收款资料，本申请的固定目标、来源及确认规则不通过改 Skill 或配置绕开。本流程不涉及会计科目或汇率，不新增分类、换汇步骤。

这是独立的可选申请，不是报销前置步骤。办理报销或餐补时，先按员工明确的本次收款资料继续当前申请，完成预览确认和提交；不要因缺少默认卡或本次换卡而转入本流程。提交成功后，若本次补录或修改了收款资料，且员工尚未说明是否长期使用，可以简短询问一次是否另提默认资料变更；员工已说“仅本次”则不再询问。只有员工主动要求或另行选择办理默认资料变更，才进入本 Skill，不自动创建或提交第二单。

从本文件向上三级确定完整包根。首次安装按[入口 Skill](../../../SKILL.md#首次安装)准备；以后复用官方 OpenYida 登录态，不注册 MCP。在包根执行：

```text
node scripts/fargowork.cjs status
node scripts/fargowork.cjs requirements default_bank_change
node scripts/fargowork.cjs prepare default_bank_change --input <绝对路径的UTF-8业务JSON>
```

仅在需要时引导本人登录。员工可以直接口述、粘贴收款资料，或自愿提供银行卡照片；优先用宿主已有图片／OCR能力识别，不另索照片或证明。由Agent整理业务JSON，不要求员工填写技术字段或阅读执行日志。照片仅用于提取字段，不放入 `attachments`，不上传到原表或保存到personal；原流程没有附件字段。

## 整理变更内容

旧资料由脚本读取本人花名册，新资料以首次读取的旧值为初值，再应用员工明确提供的修改：

| 员工资料 | 业务输入 |
| --- | --- |
| 银行账号 | `new_bank_account` |
| 银行名称 | `new_bank_name` |
| 开户城市 | `new_bank_city` |
| 开户支行 | `new_bank_branch` |
| 账户名称 | `new_account_name` |

只填写员工明确要修改的项目。旧值只是初值，不能把它当成换卡意愿；没有明确变更时询问要补充或更换什么，不提交无变化的申请。原来没有银行卡资料不构成阻塞，五项仍按原表允许为空，不额外强制补齐。后台保留五项，前台可简洁展示四组：**账号、户名、开户银行、开户城市／支行**；不能因“四组”漏掉城市、支行或户名。图片中没有的资料不猜测；沿用原值时如实标明，员工可修改或清空。户名仍与本次资料及花名册核对；差异简短提示并让本人选择继续或更正，不凭姓名猜归属或自动拒绝。

账号始终使用字符串，保留前导零和全部数字，不能传数值、科学计数法、猜测缺失号码或擅自纠正号码。不自行增加银行卡校验码规则。员工只给了掩码或识别不清时，请其核对完整内容；已有清楚的资料不要重复询问。

本流程**直接在对话展示资料，不生成HTML或MD文件**，也不使用 `editor`、`read-edit` 或导出修改文件。识别后用 `prepare` 保存草稿，按工具实际预览简洁核对新资料和变化；缺项只问识别不清或本次确有冲突的内容，不增加费用子表、币种或汇率步骤。

后续补充持续使用 `prepare default_bank_change --input <文件> --draft <同一draftId>`。省略项保留已有值，明确空字符串表示清空；同一草稿不重新用花名册覆盖初值、修改或清空。员工口述纠正后更新同一草稿，再在对话回显实际变化。用户不得指定其他 `userid`，也不传旧卡、合同公司或出纳等系统字段；后台联动正常时无感，确实影响办理才按[资料检查](../../../references/CHECKS.md)定向处理。

## 核对后提交

准备完成后执行 `node scripts/fargowork.cjs preview <draftId>`，**在对话展示**完整申请的旧、新资料和实际变化。账号须让本人能核对全部数字；空值明确显示“未填写”或“清空”。不创建额外文件，不让员工确认隐藏字段。

**展示后停止，等待本人对这份预览的新提交确认。** 最初“帮我换卡”不代替此确认；本流程只有这一次完整申请确认，不套用费用明细的两轮确认。修改资料后在同一草稿重新准备、预览并确认。

收到确认后执行 `node scripts/fargowork.cjs submit <draftId> --confirm <本次preview返回的draftSha256>` 一次，再用 `node scripts/fargowork.cjs result <draftId>` 核对结果。提交结果未知时只核查原草稿，不新建重提。成功简短报告结果及编号；内容回读未全部核对与提交失败分别说明。

“已提交”不等于审批通过或默认资料已经更新。本流程不直接写花名册，也不自动提交报销。后续办理报销时重新读取官方默认资料；尚未更新而员工已明确本次使用新卡，保留该修改并照常核对完整申请，不为同一修改重复询问。排障按[DEBUG](../../../references/DEBUG.md)，不索取凭据。

## 旧卡是否留作备用

默认卡变更申请明确提交后，只有旧卡账号可核对、本人认可且本次确实换了账号，才简短问旧卡以后是否还会用。已说明不用、不记忆的直接结束；仅改银行名称、城市或支行时不问“旧卡留备用”。原资料为空或有明显掩码时不把它当作完整真实旧卡。

本人仍会用且明确同意记忆，按[PERSONAL](../../../references/PERSONAL.md)只保存**旧卡的昵称、尾号、用途**；不保存完整账号、户名、照片，也不记新卡或自动改公司默认。本人只说“还会用”但未同意保存时，先征得保存意愿；已有明确保存／不保存意见不重复问。记忆是可选后续，不阻塞变更申请，保存失败不影响已经提交的结果。

以后本人明确要求换回旧卡，才用这些提示定位本人**已完成且审批同意**的历史报销，核对户名、让其选定后整组带入五项；无可用历史则自行提供，不能从尾号补猜完整账号。个人提示不触发自动换卡；新卡是否已成为默认，以审批后花名册实际维护为准。
