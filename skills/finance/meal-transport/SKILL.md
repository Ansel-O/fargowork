# 餐費與交通補貼

升级后建议新开会话；继续当前会话时重新加载新版入口和本流程说明。草稿按[24小时复用与刷新](../../../references/WORKFLOW-DIRECTORY.md#办理行为)：首个可核对草稿起24小时，编辑不续期、提交不全量重查；过期或用户要求用 `refresh <draftId>`，保留输入、材料和回执，展示并确认实际差异。

本流程属于财务组，沿用现有办理入口与规则。

优先遵守[公司维护源与个人选择](../../../references/FINANCE-DETAILS.md#公司维护源与个人选择)：公司币种与汇率、既定餐补公式及两组固定内部科目不被口述、网络或 personal 覆盖。不增加选科目或手填汇率步骤；交通费用仍由员工提供，财务按原流程审核。

在完整包根执行 `node scripts/fargowork.cjs requirements meal_transport`。只办理登录本人，不询问或接受他人的 userid，不搜索其他表单替代。

首先调用 `details meal_transport` 解析本人支付公司及收款币种，尚无 `items` 也可调用。唯一合法组合直接采用并告知；多个公司或币种请员工选择，填 `payment_company`、`reimbursement_currency`，历史只作建议。查不到请财务核查维护记录、查看权限及匹配条件，不断言未维护。币种明确后才按原公式计算餐补；本流程没有项目选择，不新增该问题。

只处理员工本次提供的材料，优先使用宿主已有 PDF、图片、OCR 和表格能力；已清楚的明细直接整理，不重复解析。同一加班时段的多张打卡截图合为该行证据，不重复生成餐补行；不能从餐饮发票金额推导餐补或编造加班事由。保存员工纠错、拆行与排除结果，材料冲突时集中核对。

收集 `items` 明细：`start_time`、`end_time` 用 `YYYY-MM-DD HH:mm`（公司时区 UTC+08:00，保留分钟），`reason` 是加班原因，`transport_amount` 是本次交通费，`remarks` 可选。开始时间可空；结束时间未提供时默认等于开始时间，至少需要结束时间和原因。相对日期先解析成具体日期，不把起止时间截成整日，不自行增加时长或餐补资格政策。

先将明细写为本地 JSON，运行 `node scripts/fargowork.cjs details meal_transport --input <绝对路径>`。工具仅查询本人的支付公司映射和报销币种，不因银行、部门或联系人未补齐而阻止明细整理。多支付公司时仅选择本人合法候选；餐补按原表币种公式计算，不取票据金额，交通费保持员工本次申领金额，可空或为0。固定内部科目和后台港币换算不放进员工的明细表。

用 `node scripts/fargowork.cjs review meal_transport --input <绝对路径>` 保存当前明细及材料范围；后续修订沿用 `--draft <draftId>`。**默认打开返回的 `detailEditor.path` 展示本流程 HTML，不等待用户要求**；宿主不能内嵌时提供本地 HTML 链接供浏览器打开。按[HTML 明细与修改](../../../references/FINANCE-DETAIL-EDITOR.md)保留本流程六列：**开始时间、结束时间、加班事由、餐费补贴、交通费、备注**，注明报销币种，分别展示餐补和交通费合计。口述修改回写同一草稿并重新 `review`；手动修改由员工导出文件交 Agent 执行 `apply-edit`。两种方式都展示工具新返回的 HTML，手动应用后取得对新版的新确认；导出或应用不代替确认。公式餐补与固定科目保持只读。传入 `items` 时替换整表；增删行时同步调整材料对应关系，不只回传发生变化的一行。

缺项可以先保存和展示待补 HTML，解决后展示当前完整范围，**停止并等待员工确认这版明细**。收到明确答复才运行 `node scripts/fargowork.cjs confirm-details <draftId> --confirm <本次reviewSha256>`；保存、编辑及最初办理意图都不等于确认。第一次确认只允许继续准备申请，不授权提交。

`attendance_attachments` 是必需的打卡证明文件路径数组；`expense_attachments` 是可选的报销附件路径数组，均为员工提供的本地绝对路径。两个栏分别最多20件、单件100 MiB，格式遵循表单与上传脚本检查；不用顶层 `attachments` 混装，不自行调用上传接口。细节见[附件规则](../../../references/ATTACHMENTS.md)。

首轮 `review` 的每条 `materials` 保存 `id`、`name`、原件绝对路径 `path`、`status`（`included`/`excluded`/`unresolved`）、支持哪些行的 `itemIndexes`，以及用途 `role`：`attendance` 对应打卡证明，`expense` 对应报销附件。排除项写 `note` 说明原因；未定用途的材料可暂存，确认前必须明确，不按文件名猜栏位。一个时段的多张证明可以对应同一行；确需同一文件同时支持两种用途时，保存两个不同 `id`、各自用途，并在最终两栏明确选用。改用途、范围或对应行后重新确认明细。

符合要求的原件直接使用。需要转换或合并时保留原件及其对应行，最终双栏文件之外用 `materialUploads: [{path: <输出文件绝对路径>, materialIds: [<来源材料id>]}]` 声明来源；不能把打卡证明和报销证据混为同一用途来满足必填。转换只改变输出文件时重做最终预览；改变来源内容、用途或行归属时重新确认明细。`details` 只传业务输入，材料和转换映射分别由 `review`、`prepare` 管理，不作为费用行字段。

收款资料首次从花名册带入，员工可以修改 `bank_account`、`account_name`、`bank_name`、`bank_city`、`bank_branch`，明确清空与未提供不同；账号按完整文本保留，来源无法保证完整时请员工补充准确账号，缺少必需收款账号或户名时再补问。支付公司按本人的稳定 userid 匹配，不按姓名猜测、不使用全公司目录。部门默认本人的主部门，员工明确选择时仅限本人任职部门；公司或业务归属有多个合法候选时，仅向员工展示候选名称，正常单一联动自动完成。`same_bearing_company` 默认 true，员工确需不同承担公司时设 false，再按候选选 `bearing_company`。说明可用 `description`。

本人没有默认收款资料或指定本次换卡时，按其已明确的资料继续当前餐补，将实际收款资料纳入最终申请预览；不单独重复确认已明确的修改，也不提前引导变更流程。只有员工主动单独要求先改默认资料时，才保留当前餐补草稿并转入[默认银行卡变更申请](../default-bank-change/SKILL.md)。

员工明确要求本次换卡时，按[本次换收款卡](../../../references/PERSONAL.md#本次换收款卡)在同一草稿检索本人遮掩历史候选，或自行提供；选定后整组替换五项，再纳入最终申请确认。默认仍取花名册，不因 personal 偏好自动查卡。

明细确认后，在同一草稿运行 `node scripts/fargowork.cjs prepare meal_transport --input <绝对路径> --draft <draftId>`，补齐主表及两栏文件清单。省略明细或主表字段保留原值，显式传入 `items` 替换整表、附件栏 `[]` 才清空该栏。脚本返回 `needs_input` 时只问缺少的业务信息；不展示内部字段、花名册原文或执行日志。隐藏的 HR、主管、财务、出纳和会计分类自动联动，后续出纳付款状态和日期不由员工填写。

明细、分钟时间、事由、交通金额、报销币种或材料范围发生变化时，回到同一草稿重新核对并确认；仅改收款等不影响明细的主表内容，保留第一次确认，更新最终预览。同一草稿复用已知上传结果，不因修改重新上传未知结果的文件。

准备完成后运行 `node scripts/fargowork.cjs preview <draftId>`，打开本次 `detailEditor.path` 展示完整申请 HTML：本人部门、公司和业务归属、完整收款资料、全部分钟明细、餐补及交通费各自合计、两个附件栏名称，以及每份最终文件的用途和来源材料名称，并说明首轮之后的业务变化。主表修改也回到同一草稿，重算后展示新版 HTML。**到此停止，等待员工下一条针对完整申请的新提交确认。** 第一次明细确认、选择候选或最初“帮我提交”不能替代本次答复。收到新确认再运行 `node scripts/fargowork.cjs submit <draftId> --confirm <本次preview的draftSha256>` 一次；不能将准备、预览和提交合并执行，修改后旧最终确认失效。

提交成功只报告结果和编号。上传或提交结果未知时核查原草稿，不重传、不重提；确实影响办理的问题按[资料检查](../../../references/CHECKS.md)处理。

本次餐补提交成功后，仅在补录或修改了收款资料、且员工未说明是否长期使用时，简短问一次是否另提[默认银行卡变更申请](../default-bank-change/SKILL.md)。已说“就这一次／仅本次”的不再询问。这是可选后续，不自动创建或提交第二单，不改写花名册；愿意办理后仍需独立展示变更预览并取得新确认。变更申请提交成功不代表默认资料已经生效。
