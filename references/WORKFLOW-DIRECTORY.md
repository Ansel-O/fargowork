# 流程目录与版本核对

FargoWork 3.0.0 起读取公司维护的[流程目录](https://xdlonl.aliwork.com/APP_GITLRTH76PM6J4M29F5D/workbench/FORM-3DD14956D5B6469FB2FB0C64C652FED8XFTB)。本版采用自定义页面，暂不增加普通表单。维护者发布目录后生效，员工及 Agent 办理时不编辑目录或本地规则。

`node scripts/fargowork.cjs directory` 读取完整在线状态；`workflows` 同时显示本地范围和在线目录。新目录记录会标注 `locallySupported:false`：提示更新完整包，不能自动下载或执行流程代码，也不能搜索同名表代办。

## 版本合同

流程规则版本与客户端包版本是两个独立版本。规则版本使用三段数字 `major.minor.patch`：

- patch：不影响旧客户端正确办理的修订。
- minor：兼容的可选能力；`1.0.1`、`1.1.0`、`1.1.1` 都属于同一兼容主版本。
- major：旧客户端可能办错的不兼容变化，例如 `1.x.x` 到 `2.0.0`。

每个流程独立声明规则版本，本地对应能力记录在 `config/workflow-versions.json`。主版本不匹配，或当前包低于该流程的 `minimumClientVersion`，暂停提交并提示更新。最低客户端版本也可用于要求修复同一规则主版本内的客户端缺陷。包 3.0.0 的首次规则基线为各流程 1.0.0；这两个数字不相互比较。

## 办理行为

办理前和提交前均重新读取，不用历史缓存放行。`directory.status=blocked` 或 `submissionBlocked=true` 时可以整理材料和保存明细，不能提交、绕过检查或换入口。`prepare` 会保留输入草稿并返回 `directory_blocked`，不会继续上传附件。网络、权限、重复记录、版本空值或缺少目标流程都按无法核对处理。

目录只能收紧本地支持范围。本地 Moka 指引和固定目标不会被远端 `active` 或新的表单地址重新启用。公司停用或迁移流程后，保留草稿并按公司渠道核对办理方式。

升级、跨日或业务资料变化时，保留材料和员工已确认的合法选择，重新准备。相关变化撤销旧确认；兼容版本变化但业务内容未变，不要求员工重选未变的明细。完整申请仍需展示后取得新的提交确认。

已经发出提交尝试的草稿先用 `result` 核查；目录不可读或流程停用不妨碍查询原结果。结果未知时不要重建、重传或重复提交。

## 读取与维护边界

官方 OpenYida 读取固定自定义页 Schema，在唯一 `YidaCodeCanvas.props.code` 内定位 `FARGOWORK_DIRECTORY_V1_BEGIN/END`，只用 JSON 解析器读取中间的结构化数据。FargoWork 不执行页面 JavaScript。目录绑定公司、应用和固定页面；任何格式异常都会阻止提交。

维护者按实际规则维护目录，版本与目录修订需可追溯。回滚也发布新修订，不改写旧发布记录。修改后应核对普通员工账号通过同一 CLI 命令能够读取；管理员可读和网页能打开都不能代替该验收。页面不存员工、银行卡或业务申请数据。

这属于客户端防误用机制。员工可改本地文件，OpenYida 或其他客户端也可能直连，因此不能宣称具备不可绕过的权限保障或防篡改认证。2.9.1 及更早版本未读取此目录，必须先明确升级；设置最低版本不能远程停用这些旧包。未来若需要统一约束所有写入口，应由可信接收端校验，另行评估平台能力或 Server。
