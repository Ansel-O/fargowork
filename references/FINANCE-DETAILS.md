# 财务明细

费用报销、出差费用报销、正式对外付款和餐费交通补贴按“本次材料 → 必要建议和计算 → 修改并确认明细 → 补主表 → 确认完整申请”办理。命令和语义输入文件由 Agent 在完整包根维护；员工只需提供材料、修改和确认业务内容。下列八列和科目例子属于费用报销；其他流程使用各自列和规则。体检报销为单笔金额，仍按其 Skill 完成一次完整申请确认。

## 读取和整理本次材料

优先使用员工或宿主已有的 PDF、图片、OCR、表格及文件处理能力；只要结果足以整理费用，就不重复解析或另装指定工具。本包不提供专属 OCR 或表格编辑器。只处理本次提供的资料，不自动搜索邮箱、聊天或历史报销补材料。

一笔实际费用一行，同笔费用的发票、订单、付款截图归为同一组证据；一张付款单含多笔实际费用时可拆行。区分本次付款、套餐标价、折扣和退款，总额已含税就不再加税。内容用途足够时直接建议分类；金额、币种、费用归属或用途确实不明才补问，不把所有识别数字相加，不从“$”猜币种。

采用流程既有语义字段：

| 输入 | 用途 |
| --- | --- |
| `items[].description` | 每笔费用的内容详情；可纳入有业务意义的日期和用途 |
| `items[].amount`、`original_currency` | 本次申请的原币金额与币种；金额优先保留十进制字符串，不猜数值 |
| `items[].expense_category`、`account` | 普通费用的合法类别与科目配对 |
| `items[].classification_reason`、`remarks` | Agent 的简短建议依据与员工备注；理由不写入平台，备注可空 |
| `payment_company` | 需要选择时，采用本人映射中的支付公司；工具由此取得报销币种 |
| `is_project`、`project_name`、`project_expense_category` | 仅项目报销需要；该分支按项目合法类别限制各行科目 |

不传原生字段、手填汇率或计算结果。先确定影响八列的必要上下文；银行账号、申请部门和其余主表业务线留到第一次明细确认之后。

## 推荐科目并匹配汇率

```text
node scripts/fargowork.cjs details expense_reimbursement --input <绝对路径UTF-8业务JSON>
```

`details` 仅作只读查询和计算，不创建草稿、不上传、不提交。传费用语义输入，不传 `materials` 或 `attachments`；材料范围在下面的 `review` 中保存。

- `needsInput` 中标记 `resolver: agent_recommendation` 的项由 Agent 处理。读取每行内容和 `recommendationContext.allowedPairs`，选择符合实际用途的完整类别/科目配对，按 `categoryInputKey`、`accountInputKey` 回填；项目类别使用主表字段。不能跨配对组合、选目录第一项凑数，或只把目录转给员工。
- 把简短依据写入对应行 `classification_reason`，再次调用命令校验。用户已有合法选择应保留；建议足以判断时直接填好，再随明细统一核对，不逐项增加确认。
- 工具按原币种→公司报销币种取公司维护汇率并计算每行报销金额，合计使用各行已舍入结果。不要换用市场汇率，也不要要求员工填写已有汇率。费用类别尚待建议时，已知金额仍可算；支付公司未确定时，汇率及报销金额为 `null`，不能填0或1。目录或汇率缺失按返回提示联系 Finance，不能自行补造。

## 保存材料范围和可编辑明细

```text
node scripts/fargowork.cjs review expense_reimbursement --input <绝对路径UTF-8明细JSON>
node scripts/fargowork.cjs review expense_reimbursement --draft <draftId> --input <绝对路径UTF-8明细JSON>
```

第一次 `review` 保存本地首轮草稿并返回 `draftId`、`reviewSha256`、`preview` 和 `needsInput`；后续在同一草稿修订。此阶段只读业务来源，材料文件只在本机检查，不上传或提交。

本次材料可用可选 `materials` 数组记录。每项如下；这些字段由 Agent 整理，不要求外部解析工具输出专属格式：

| 字段 | 含义 |
| --- | --- |
| `id`、`name` | 本次材料的稳定标识与员工能辨认的名称 |
| `path` | 可选的本地绝对文件路径；提供时检查文件并计算内容摘要，不上传 |
| `status` | `included` 已纳入、`excluded` 员工明确排除、`unresolved` 尚未处理清楚 |
| `itemIndexes` | 对应 `items` 的从0开始的行索引；一份材料可支持多行，一行也可引用多份材料 |
| `note` | 必要说明；排除时必填，其他情况按需保留 |

`included` 至少对应一个有效行索引；`excluded` 无行索引并写明原因；`unresolved` 可暂不对应行，草稿仍保存但不能完成明细确认。增删或拆分费用后同步修正对应索引。材料没有页码、坐标或置信度不阻塞；未处理的材料不能悄悄省略。

`review` 和同草稿 `prepare` 合并本次顶层语义输入；省略的字段沿用原值。显式 `items` 替换整张明细表，不能把单行修改当成完整表传入。省略 `materials`、`attachments` 各自沿用旧集合，显式 `[]` 各自清空；`materials` 是来源及费用归属，`attachments` 是最终上传集合，二者用途不同。通常在明细确认后才确定并传最终附件。

## 展示与修改

展示当前 `preview` 的八列：**费用类别*、会计科目*、内容详情*、原币金额*、原币种*、汇率*、报销金额、备注**，标明报销币种、各原币小计和报销总额。多币种不能直接相加。分类依据简短附在表后；隐藏路由、主管、内部标识正常时不展示。

可使用宿主已有的可编辑表格，或让员工在聊天中按行增删、修改、排除、拆分和纠正 OCR。Agent 将修改回写语义输入，重新 `review`，只重核受影响行及更新合计，保留其他已改内容。汇率和报销金额由工具重算，用户可以提出异议，但不把表格中的手改汇率当作维护表来源。员工直接提供的合规明细也走同样检查，不要求先生成或重读票据。

`needs_input` 不等于每项都要问员工，先完成 Agent 能解决的建议。`details_ready` 是只读结果；`awaiting_detail_confirmation` 表示首轮草稿可以展示，两者都不是员工已经确认。缺项未解时可展示待补明细，不能把原币小计称为报销合计。

## 两次确认与继续办理

1. 展示当前八列及材料范围后停止，等待员工新答复。收到对这一版明细的明确确认，才执行 `node scripts/fargowork.cjs confirm-details <draftId> --confirm <本次reviewSha256>`。返回 `details_confirmed` 后继续补主表；编辑、保存、最初的办理意图或另一个 Agent 的答复不能代替本人确认。
2. 按[费用报销 Skill](../skills/finance/expense-reimbursement/SKILL.md)补齐主表和最终附件，使用 `prepare expense_reimbursement --draft <同一draftId> --input <业务文件>`。`items` 省略时保留已确认明细；不应让员工重新填写。准备过程复查目录和汇率，明细变化则回到首轮预览与确认。只改收款等不影响明细的主表信息可保留首轮确认。
3. 准备完成后调用 `preview <draftId>`，展示完整申请及最终文件，停止并等待新的提交确认。之后才执行 `submit <draftId> --confirm <本次draftSha256>` 一次。第一次明细确认不是提交许可，不能将两次确认合成一次执行。

修改八列、报销币种、材料范围或对应关系后，重新展示受影响明细并取得确认。仅将相同证据转换或合并为合规上传文件、不改变原材料语义及费用范围时，保留首轮确认，最终预览展示文件变化。提交前再次检查导致可见明细变化时也需返回确认，不能自动接受新金额或重试提交。

两个摘要用于绑定当前内容，不能证明员工确实同意。Agent 必须展示并等待本人新答复；技术标识、逐步日志和测试报告不交给员工。成功与回读核验分开报告；结果未知用同一草稿 `result` 核查，不另建申请重提。

## 出差费用报销

出差费用报销使用 `trip_expense_reimbursement`，完整步骤见[出差费用报销 Skill](../skills/finance/trip-expense-reimbursement/SKILL.md)。顺序同样为 `details` → `review` → 展示并等待新确认 → `confirm-details` → 同草稿 `prepare` → `preview` → 等待新的提交确认 → `submit`。

- 明细列按返回的本流程 `preview` 展示，包含行程/日期、关联出差、各项实报、原币及换算、餐补和备注，不套八列。可空字段保留空值，0是有效的明确金额。
- 默认本人；获准代办时先按姓名查询并明确选择候选，再按选定报销人的支付公司、币种、关联出差和必要资料办理。关联单限该报销人已结束且审批通过的正式出差；原表例外只免关联必填，不改变有效候选范围。
- 票据原币用于各项实报费用；餐补以支付公司的报销币种为单位，建议来自区域和日期规则。保留员工明确修改的 `allowance_amount`。相同或重叠行程拆币时只建议一次餐补，其他相关行默认0；业务冲突集中核对。
- `materials` 继续使用前述本次材料结构和 `items` 行索引；增删/拆行时同步修订对应关系。重读、转格式或合并文件不能覆盖员工修正。
- 首轮确认绑定真实报销人、真实关联单、餐补币种、明细和材料范围；这些内容变化后重新确认受影响明细。银行等无关主表修改可保留首轮，仍需更新最终预览并等待新的提交确认。

同一草稿中的已知上传和未知提交处理沿前述规则；不因重试改用另一草稿，不将本地检查或提交成功描述为审批通过。

## 正式对外付款

使用 `external_expense_application`，详见[正式对外费用 Skill](../skills/finance/external-expense-application/SKILL.md)。顺序为 `details` → `review` → 展示并等待明细确认 → `confirm-details` → 同草稿补主表与附件 → `prepare` → `preview` → 等待新的提交确认 → `submit`。

- 普通款展示费用类别、会计科目、付款内容、本次付款金额和备注，并标明本单币种及合计。项目款另有逐行项目部门与业务归属，共用项目主表类别，不改成逐行独立类别。
- 每笔实际付款一行，同笔合同、账单、发票与付款截图只作证据归并。区分合同总额、已付、订金、尾款与本次付款；`items[].amount` 只填本次申请额，不将这些数字相加。
- 本单各行使用统一付款币种。混合币种材料先核对本次各项实际支付币种及金额；不能直接相加、猜汇率或自动拆成多笔真实申请。工具沿正式表规则取得维护汇率及后台HKD换算。
- Agent根据付款内容填好合法费用类别、科目配对和建议依据，再统一展示。首轮只先明确影响明细的支付公司、币种及项目范围；银行、最晚付款日期、无关主表业务线和历史收款留到明细确认后。
- 收款方三项来自本次外部付款资料；仅员工明确需要历史参考时查本人候选，整组带入再保留明确修改，不将不同收款方的旧字段拼接。账号始终为完整字符串。
- `materials` 沿用材料行索引和纳入/排除规则。最终 `attachments` 从本次已纳入材料及必要转换件中选取，不把原始整批、重复凭证和排除材料默认全部上传。最多30件、单件100MiB，正式与示例草稿分开。

## 餐费交通补贴

使用 `meal_transport`，详见[餐费交通 Skill](../skills/finance/meal-transport/SKILL.md)，同样先确认本流程明细，再确认完整申请。明细为开始时间、结束时间、加班事由、餐补、交通费和备注；分钟时间保留完整日期，开始可空，结束未提供时沿用开始。不能合并不同加班时段或从材料编造事由。

本人支付公司及币种在首轮取得。餐补按既有币种公式计算，不取餐饮发票金额；交通费采用本次实际申请金额，两个合计分别展示。固定隐藏科目及后台HKD转换沿用原规则，不增加用户选科目或手填汇率的步骤。银行与其他主表资料在明细确认后补。

餐补的材料用途由本流程固定定义：

| `materials[].role` | 证据用途 | 最终附件输入 |
| --- | --- | --- |
| `attendance` | 打卡证明 | `attendance_attachments`，必填 |
| `expense` | 报销凭据 | `expense_attachments`，原表可选 |

其他材料字段仍是稳定 `id`、可辨认的 `name`、可选绝对 `path`、`status`、`itemIndexes` 和必要 `note`。已纳入材料须明确用途；不清楚时可以保存待补草稿，明确后再确认。用途、对应行、纳入范围或原文件内容变化均使明细确认失效。原件可以改名或迁移，内容相同时仍按已确认用途匹配。

首轮只在本机整理材料。最终按两栏分别选择文件，每栏最多20件、单件100MiB，不能把报销凭据放入打卡栏凑必填。原件按内容匹配已纳入材料；转换或合并件保留原件，以可选顶层 `materialUploads` 说明输出和来源：

```json
{"materialUploads":[{"path":"C:/Documents/本次打卡合并.pdf","materialIds":["attendance-1","attendance-2"]}]}
```

此映射只用于最终上传，不能修改金额或覆盖明细。多个来源必须都已纳入且用途相同；不把打卡与报销两类材料合到同一附件栏。输出文件仍在对应的附件数组里选择。省略 `materialUploads` 沿用已有映射，显式 `[]` 清空；仅更换合规转换件而源材料、明细及用途不变时，保留首轮确认，最终预览重新核对文件及来源。脚本会在上传前检查来源/栏位映射，完整预览分别展示两栏文件和附件来源。

其他流程没有声明材料用途时，继续各自既有材料格式，不传餐补专用的 `role` 或 `materialUploads`。
