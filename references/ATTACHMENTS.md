# 原生附件

出差、采购、硬件、软件、对外付款、费用报销、出差费用报销、体检报销、合同、名片、用印和餐費與交通補貼共用包内附件脚本，使用同一官方 OpenYida 身份；付款和合同正文按原表单要求至少一件。员工提供文件就是本次附件来源，不改用外部附件服务器或临时上传程序。

正式假期、销假及已迁移 HR 流程只引导前往 Moka，不在本包收集或上传附件。已移除或停用流程的旧草稿不能继续办理。

- 普通流程在业务 JSON 顶层传 `attachments: ["本地绝对路径"]`。支持 PDF、PNG、JPEG、GIF、WebP、TXT、DOC、DOCX、XLS、XLSX、PPTX；数量与单件大小按目标表单 Schema 检查，当前常见上限为9件、20 MiB。
- 正式对外费用使用顶层 `attachments`，至少1件、最多30件、单件100 MiB；先确认本次付款明细和材料范围，再从已纳入范围选择最终文件。上传绑定当前流程的固定目标，不互换附件引用或草稿。
- 费用报销和出差费用报销使用顶层 `attachments`，至少1件、最多20件、单件100 MiB；先确认本次明细及材料范围，再准备最终上传文件，不因合并凭证减少费用行。
- 体检报销使用顶层 `attachments`，至少1件、最多9件、单件100 MiB。与金额、收款资料一起纳入完整预览，等待新的提交确认；没有费用子表，不要求先确认八列明细。
- 正式采购的附件可选，最多9件、单件20 MiB；硬件和软件申请的附件也可选，最多9件、单件100 MiB。这三个流程的附件放在业务 JSON 顶层，不放进采购或硬件明细行。
- 用印把文件路径放在各自清单行的 `items[].attachments`。每行最多9件，单件最多100 MiB；脚本将每行附件绑定到该行，并在预览、草稿冻结和回读中保留行号归属。同一文件可以用于不同行，已完成上传会复用；同一行不要重复添加同一文件。
- 餐費與交通補貼先按[本流程材料用途](FINANCE-DETAILS.md#餐费交通补贴)整理并确认分钟级明细；`materials[].role` 分别为 `attendance` 或 `expense`。最终使用必需的 `attendance_attachments`（打卡证明）与可选的 `expense_attachments`（报销附件），分别最多20件、100 MiB；只接受 PDF、JPEG/JPG、PNG、DOC/DOCX、XLS/XLSX。原文件按已确认用途匹配；转换/合并件通过 `materialUploads` 关联已纳入的同用途源材料，不能通过改名或换栏规避用途对应。
- 若流程 Skill 指定多个附件栏，按各栏名称分别提供文件，预览也分别展示。每栏独立检查必填与数量，不能用另一栏的文件替代；按对应 Skill 的输入格式操作，不自行指定原生字段。
- `prepare` 自动检查文件、获取签名、上传、登记并绑定该草稿。Agent 不接触签名/token，不把下载地址当附件字段，不自行复制他人附件引用。
- 增加、删除或更换文件都在同一草稿 `prepare ... --draft <draftId>` 中完成；未修改的已知附件复用，最终清单以这次输入为准。随后重新读取预览，让员工看到文件名并确认。
- 名片、费用报销、出差费用报销、体检报销和正式对外费用支持同一草稿的部分补充答复：省略 `attachments` 保留之前指定的文件，显式 `attachments: []` 清空。餐费交通两栏各自省略保留，显式空数组只清空对应栏；其余流程按各自 Skill 提交本次完整文件清单。材料范围与最终上传集合各自维护，不把清空上传集合当作排除原始证据。
- 最终预览只展示员工选择的文件，不展示对象名、签名、地址、内部引用或摘要。不得在员工确认前提交业务流程。
- 上传结果未知时停止，不自动重传或另建草稿；提供错误码请 IT 核对。流程已提交但回读暂不可用时保留成功状态，不能为了附件核验再次提单。

用印的文件必须放进对应明细行，例如下面的业务输入形状；文件路径替换为员工本人提供的真实绝对路径：

```json
{"company":"已选公司","items":[{"seals":["公章"],"copies":1,"attachments":["C:/Documents/合同.pdf"]}]}
```

原生上传实现在 `scripts/lib/native-attachment.cjs`；主表与明细行的映射、绑定和预览在 `shared/workflow-attachments.cjs`，由统一入口调用。不要单独复制此文档或要求 Agent 重写上传逻辑。
