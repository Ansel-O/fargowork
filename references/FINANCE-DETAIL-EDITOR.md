# 财务明细编辑与回读

先按本流程确定公司和收款／付款币种，涉及项目时明确项目归属。合法组合唯一直接采用，多个才询问；体检固定CNY，保留原合同公司默认及可空规则；银行卡变更不增加币种步骤。首个可核对草稿起24小时复用公司资料，普通修改不全量联网复查；缺新项才补取，过期或主动要求时 `refresh`。

## 默认 HTML，同一草稿保留 MD

费用报销、出差费用报销、正式对外付款和餐费交通补贴默认提供本机HTML明细。体检报销和银行卡变更直接对话，不生成HTML或MD编辑页面。

明细阶段由工具准备页面：优先打开返回的 **`detailEditor.url`**，由侧边栏或浏览器显示，不能把后台MD路径误当HTML。FargoWork自动启动和复用随包Node保存程序，员工无需选文件、运行终端或导出。只在本机当前草稿范围保存，不提交宜搭。费用报销、出差报销、正式对外付款和餐费交通在明细确认后，`prepare` 和最终 `preview` 转为对话核对主表及完整申请。所有流程的完整申请都在对话核对，不另生成整单HTML，已有明细页继续保留。

若工具返回MD兜底，或宿主不能访问本机页面，打开 `detailEditor.path` 对应的原MD，用文件编辑器保存；不得假称HTML已打开或保存成功。用户主动偏好MD时用 `editor <draftId> --format md`；需要HTML再用 `editor <draftId> --format html`。已有草稿与确认规则不因展示方式改变。

## 三种答复与同一份数据

1. **“没有问题”且没有修改：** 沿本流程当前确认步骤继续，不重解析材料、重生成草稿或重查公司资料。
2. **在HTML改好并保存，或保存了原MD：** 员工说“改好了”或确认修改后，先 `read-edit <draftId>` 回读当前原文件，复用公司资料、共享代码重算，再展示受影响行和新合计并按原规则确认。HTML保存成功只代表本机文件已保存，不能跳过回读应用或视为提交许可。
3. **口述修改：** Agent更新同一草稿的语义输入。费用、出差、正式付款和餐费交通的明细修改用 `review ... --draft <draftId>`，主表修改用 `prepare ... --draft <draftId>`；体检和银行卡变更沿原 `prepare`。主表变化在对话回显，有明细页的流程才更新页面；各自确认次数保持。若工具提示已有未应用文件修改，先回读，不能生成文件覆盖员工保存的内容。

保存按钮与页面收到的Ctrl+S使用同一路径；若宿主截获快捷键，使用页面“保存”。关闭窗口不等于保存，不承诺自动保存。页面显示失败或修订冲突时保留输入，明确尚未保存，核对当前草稿；不猜测覆盖。成功后不需要导出、上传、截图或搜索下载目录。普通修改不做整页截图检查。

```text
node scripts/fargowork.cjs read-edit <draftId>
node scripts/fargowork.cjs editor <draftId> --format md
```

显式提供另一份已保存MD时才用 `apply-edit <draftId> --input <MD绝对路径>`。文件绑定草稿和修订；稳定行身份用于材料归属与重排，不进入业务字段。省略、清空和0分别保留。显式 `items` 替换整表，不能只传一行；删行后材料无归属须核对，不静默丢弃。

## 明细模板与候选

有明细页的流程，HTML与MD兜底保留同一套业务字段。体检和银行卡变更直接对话，不创建或导入明细文件。

| 入口 | 明细结构 |
| --- | --- |
| 费用报销 | 类别、科目、内容、原币金额、原币种、报销金额、备注；项目名及共同类别顶部一次，原项目字段继续后台保存 |
| 出差费用报销 | 每条独立成块，同行程的日期、关联出差、四项费用和差旅津贴放在一起 |
| 正式对外付款 | 类别、科目、付款内容、本次付款金额、备注；统一主表币种，项目保留逐行分配 |
| 餐费交通补贴 | 开始时间、结束时间、加班事由、公式餐费补贴、交通费、备注；普通序号辅助对应 |

醒目提示：**只需修改明细，无需自己计算总额。保存后告诉Agent“改好了”，金额和总额由代码重算。**

类别和科目保留公司目录完整原文。Agent结合每行实际用途推荐一组并给一句理由，附1至2个合理备选；没有合理备选就不凑数，不编置信百分比，不把候选混入实际字段。已有合法明确选择保持，固定科目不开放更换。原有按类别分组的展示元数据继续兼容其他流程和MD：

```json
{"recommendations":[{"category":"公司目录完整类别原文","account":"公司目录完整科目原文"}]}
```

省略沿用，`[]`清空；工具校验合法配对，推荐元数据不提交宜搭。餐费交通、体检不新增科目。

费用和正式付款的HTML推荐需逐行绑定，按**首选、备选**顺序提供，包含首选本身；`rowNumber` 从1开始，`description` 必须与该行当前完整用途相同，两项成对填写，`reason` 为不超过300字的简短理由：

```json
{"recommendations":[
  {"rowNumber":1,"description":"本行当前完整用途","category":"公司目录完整类别原文","account":"首选科目完整原文","reason":"结合本次用途的一句建议依据"},
  {"rowNumber":1,"description":"本行当前完整用途","category":"公司目录完整类别原文","account":"合理备选科目完整原文","reason":"这个备选适用的具体情况"}
]}
```

示例文字须替换成本次真实用途和工具返回的合法配对，不能照搬科目编号。实际 `items[].account` 仍只填一项，已声明 `classification_reason` 的流程可用它保留当前建议依据。HTML优先取匹配本行用途及类别的元数据首项作为首选；员工手动改当前科目不自动重排推荐，也不能以推荐覆盖其实际选择。用途或类别变化后不显示旧建议，不把同类别其他行的候选自动套过来。无逐行元数据时，当前合法科目有理由可作为默认建议，否则只显示当前选择及暂无适用建议，不抓目录前几项凑数。旧二字段元数据用于原有MD分组，不当作这两个HTML入口的逐行推荐。只读的 `rowRecommendations` 由编辑器生成，不作为业务输入。

明细模板不展示汇率。手改汇率、派生金额、合计、建议天数、公式餐补或后台港币金额不作为输入，后台用已有公司资料重算。各原币分别小计，报销总额按收款币种计算，不混币相加。

**费用：** 使用专用紧凑七列HTML：费用类别、会计科目、内容详情、原币金额、原币种、报销金额、备注。类别／科目原文完整显示；原币种与换算报销金额只读，其他业务内容按合法范围修改。每行科目可查看默认建议理由、少量合理备选，也可展开当前类别全部合法科目。项目名／共同类别在顶部一次，行内用项目科目；项目部门和业务层级仍按原字段及规则在对话选择，明细不展示、不迁移字段。银行、部门、业务层级、汇率及完整申请不进入页面。最终在对话核对主表、实际收款、已确认明细合计和附件，再等待新的提交确认。

**出差：** 每块包含出发地、目的地、地区、完整起止日期、本行关联出差、四项实报费用、原币种、报销金额、差旅津贴币种／标准／建议天数／金额及备注。原表“飞机、车船票款”包含火车票；退票费放其他费用及备注，不造列。津贴按行程顺序只自动计前行未覆盖的日期，首尾包含、重叠归前段；真实行程日期不改。明确手改津贴含0及清空保留，自动建议不因保存变成人工覆盖。

出差使用独立紧凑HTML模板：只开放四项费用、津贴、合法境内地区及项目科目；行程／日期／关联／币种只读，其他改动口述处理。无增删行、空下拉、完整主表或后台计算展示。项目名／类别只出现一次，项目业务层级整单确定一次并保留后台字段，HTML和MD明细均不逐行展示；项目科目有备选才下拉，保留完整原文、默认建议及一句理由。改选后清旧理由。最终`preview`返回对话确认，明细文件继续保留，主表不再生成HTML。

**正式付款：** 专用紧凑五列HTML：费用类别、会计科目、付款内容、本次付款金额、备注。统一主表 `currency`，不增加各行原币种；只合计本次付款，不把合同总额或历史已付相加。逐行默认建议、最多两项合理备选与全部合法科目入口沿费用方式。项目名称／共用类别顶部一次，项目部门与业务层级沿原逐行规则在对话确定，后台字段保留、不迁移；明细不展示银行、部门、汇率或完整申请。最终在对话核对本次外部收款资料、完整账号、公司币种金额与附件，等待新的提交确认；不套员工花名册，合同、用印和费用关联规则不变。

**餐费交通：** 专用紧凑六列HTML：开始时间、结束时间、加班事由、餐费补贴、交通费、备注。时间组件保留日期和分钟，开始默认加班当天18:00，用户明确18:30或其他值则采用其值，清空也保留。结束优先从打卡附件／截图读取，用户纠正优先；缺失或含糊直接问，不猜结束、不以开始回填，不猜前一天或用申请日替代。餐补按原公式只读，交通可改。打卡证明和报销票据分栏；明细只显示公司／币种、真实字段、合计及短提示，不给员工材料台账或主表。明细确认后补主表，最终在对话核对完整申请及两栏文件名。

**体检：** 不生成HTML、MD小样或正式编辑页面，不调用编辑和文件回读入口。直接 `prepare` 后在对话 `preview`，显示固定CNY、原金额及1500元封顶结果、公司、花名册默认或明确修改的收款五项及附件名。口述修改同草稿 `prepare` 并由代码重算，只等一次新的完整申请确认。公司沿原合同默认和“有银行账号”目录，原可空字段不强填；正式员工与一年一次仍由原表校验。

## 保留原确认次数

费用、出差、正式付款和餐费交通：展示明细→修改并确认明细→补主表→对话展示完整申请→新确认→提交。第一轮用当前 `reviewSha256` 执行 `confirm-details`；最终 `preview` 展示后停止，等待新确认，再用当前 `draftSha256`提交一次。

体检和银行卡变更仍只有一次完整确认。保存、回读、应用、摘要或最初办理意图都不能代替确认；未变化的已确认明细不重问，有变化只核对受影响内容。页面不提供直接提交接口。

## 银行卡变更直接对话核对

不调用 `editor`、`read-edit` 或 `apply-edit`。文字或自愿照片提取账号、户名、银行、城市、支行，前台可合组，不漏原生五项、不猜缺失。照片不上传原表。`prepare`后对话核对，修改仍同草稿，`preview`后一次新确认提交。旧文件不导入，原草稿保留。

变更提交后，仍会使用的旧卡经本人同意才存personal昵称、尾号、用途，不存完整资料；以后明确换回才从本人已完成且同意的历史核对，缺记录自行提供，见[PERSONAL](PERSONAL.md)。

旧版导出文件仅属历史，本版不要求员工导出交回。

本机文件含申请资料，只保存在当前草稿目录，不进入公开仓库或长期personal。Node保存不是公司服务端业务鉴权，平台权限和审核仍沿既有规则。
