# 财务明细预览与手动修改

财务申请先确定支付公司及收款／付款币种，再整理明细。涉及项目的流程还要明确项目归属。用户已经说清的内容直接沿用；只有一个合法公司／币种组合时直接展示采用，多种组合才需要选择。

**七个财务入口在核对草稿时默认展示本流程的可编辑 HTML，不等待用户额外要求。** 工具固定每个流程的标题、列名、完整日期和合计，绑定当前草稿；Agent不另写一张表替代。单笔也生成 HTML，可附一句摘要；体检、默认卡按原字段展示，不制造费用子表。

用户可以口述或在 HTML 手动修改。页面与口述共用 `shared/finance-calculations.cjs` 的纯计算代码，包含同一十进制运算和津贴规则；页面改动即时显示可计算结果，导出应用后回到同一草稿。未取得必要公司数据时显示待补，不猜数或把未知金额显示为0。

## 默认展示与两种修改方式

`review`、`prepare`（包括待补资料）和 `preview` 自动生成当前草稿的 HTML，返回 `detailEditor.path`。Agent 直接打开或提供该文件的可点击链接，并说明“可以直接告诉我改哪里，也可以在页面编辑后导出修改文件交给我”。无需另外运行 `editor`，也不询问用户是否要 HTML。四个有明细阶段的流程从 `review` 开始展示，体检、默认卡和 Demo 从 `prepare` 开始展示；以工具返回的阶段及待补项为准，未完整的页面不用于提交确认。

宿主有文件呈现能力时直接用它展示本次 HTML；否则提供可点击的本地 HTML 入口供浏览器打开。每轮呈现最新修订并简短概括改动，不只说“已生成”、贴裸路径或沿用旧表。文件缺失或需要重新打开时，使用以下恢复入口：

```text
node scripts/fargowork.cjs editor <draftId> [--output <HTML绝对路径>]
```

HTML 生成失败时保留草稿，恢复并展示后再请求确认，不声称用户已经看过。汇率、固定科目和派生结果只读；公司、币种、项目、科目、关联出差从已核验候选选择。有效期内复用取得的合法资料，缺新值只补取对应来源，不因改一格刷新整单。存在明细表时允许增删、复制、调整顺序和材料归属，其他流程保留单笔或对照结构。

**自然语言修改：** Agent 将用户指定的修改回写同一草稿；明细阶段调用 `review ... --draft <draftId>`，主表阶段按原流程调用 `prepare ... --draft <draftId>`。展示返回的新 `detailEditor.path`，简短说明受影响行、金额或待补项，保留其他内容；明细变化仍按原规则重新确认。用户明确接受或替换已展示科目的处理见[科目推荐与独立备选](FINANCE-DETAILS.md#科目推荐与独立备选)，不重复询问未变化的行。

**手动修改：** 用户在 HTML 中修改后点“导出修改文件”，将下载文件交回 Agent。Agent 运行：

```text
node scripts/fargowork.cjs apply-edit <draftId> --input <修改文件绝对路径>
```

命令本地核验输入、用共享代码重算并更新草稿，返回新版 `detailEditor.path`；在24小时有效期内不全量联网重查。展示新版及实际变化，按原流程确认。仅打开页面、编辑、导出或成功应用不等于明细确认或提交授权；页面没有直接提交入口。

每次修改后使用新版页面，旧修订不能覆盖新草稿。改项目时清除旧项目依赖分类，用已有合法候选核对新项目、部门及科目，缺项才补取；费用和真实日期保留。用户主动要求或24小时过期时用 `refresh <draftId>`，保留材料与已知回执，展示差异并确认受影响内容；正常编辑不延长有效期。

## 七个入口各自保留的内容

| 入口 | 预览与编辑 |
| --- | --- |
| 费用报销 | 原八列、项目归属、每行合法类别与科目、材料关系 |
| 出差费用报销 | 完整行程日期、逐行关联出差、飞机／车船、住宿、交通、其他费用、差旅津贴及备注；津贴建议天数独立显示 |
| 正式对外付款 | 本次付款金额及统一币种、合法类别／科目，主表阶段再补收款资料及关联业务 |
| 餐费交通补贴 | 分钟级起止时间、加班事由、交通费；公式餐补只读，打卡证明与报销附件用途分开 |
| 体检报销 | 单笔原申请金额、人民币封顶结果及原收款资料，没有虚构费用子表 |
| 默认银行卡变更 | 原资料对照和新五项资料，账号始终作为字符串 |
| 对外付款 Demo | 明确标注 Demo，按独立测试流程字段展示 |

四个有明细阶段的正式财务流程继续采用“展示 HTML 明细 → 修改并确认明细 → 补主表 → 展示完整申请 HTML → 确认提交”。第一次确认使用当前 `reviewSha256`；补主表后执行 `preview`、展示最新 HTML，再等待新的提交确认，使用本次 `draftSha256` 提交。HTML 路径、导出动作和内容摘要都不能代替用户确认。

体检、默认银行卡变更及 Demo 只保留自身的一次完整申请确认，不另增明细确认。首轮明细页面不会提前展示需要到主表阶段才补的银行资料。工具顶层 `nextAction` 继续决定办理步骤，`detailEditor` 只提供本次应展示的页面，不改变确认流程。

复制一条明细后应调整金额和日期，避免把同一笔费用重复计算。删除明细时，失去对应行的材料会变为待确认；不纳入的材料须写明原因。增加新附件仍交由 Agent 处理，页面不允许直接改写原文件路径。

## 适配说明

此 HTML 的样式和脚本全部内嵌，可离线打开；没有登录、网络请求或业务提交接口。手动修改通过导出文件回传，不声称网页能自动保存到 Agent。宿主能否内嵌只影响打开方式，不改变默认提供 HTML 和原有确认要求。

`shared/finance-detail-editor.cjs` 提供：

- `createEditor({workflow,draftId,input,review,prepared,materials,stage,choices,rowIds,previousDocument})`：生成 `document`、`html`、`rowIds` 和 `baseRevision`。`stage` 为 `details` 或 `application`。
- `revision({workflow,draftId,input,review,prepared,materials})`：生成当前内容摘要；命令入口也可传入自己的 `revision`，但导入时必须采用同一口径重新核对。
- `collectChoices(...results)`：收集 `editorChoices`、待补字段候选及既有科目合法配对。
- `applyEdit({document,edit,currentRevision,input,materials})`：拒绝错误草稿、旧修订、非法字段或候选，返回合并后的语义 `input`、`materials`、`rowIds`。调用方随后执行原工作流，再持久化与展示结果。

候选以语义字段为键，例如 `payment_company`、`items[*].original_currency` 或 `items[0].trip_instance_id`；值为字符串数组或 `{value,label}` 数组。关联项只显示名称，真实关联 ID 由工具持有。新增行使用有效快照中的合法候选，按当前身份、本次报销人、取得时的审批状态及分类配对本地核验，缺新候选只补取对应来源。

修改文件绑定流程、草稿及基础修订，材料用稳定行标识关联，导入时转换为当前行序。展示标识不进入宜搭业务字段。缺省、清空和0分别保留；未动过的自动差旅津贴建议不因导出变成手工覆盖，用户明确修改的值含0则持续保留。

模板和修改文件包含本次申请资料，应保存在本地草稿目录，不加入公共仓库或作为个人长期记忆。产品模板及测试只使用合成数据。
