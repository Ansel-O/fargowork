# 其他企业如何适配

本指南面向其他企业的流程维护者。当前发布包是 Fargo 的具体实现，包含公司标识、表单字段和业务规则。外部员工不能直接用它办理本公司的申请；应先由维护者完成适配、验证和内部交付。

代码按 [Apache-2.0](../LICENSE) 开放。代码的使用许可与企业数据、平台账号的访问权限是两回事；获得代码不会获得 Fargo 或其他企业的资料权限。

## 先理解文件分工

| 位置 | 维护内容 |
| --- | --- |
| [config/company.json](../config/company.json) | 企业、宜搭应用及域名；花名册连接器、连接引用和应用 AgentId。 |
| [config/sources.json](../config/sources.json) | 公司、部门、汇率、会计科目等维护来源，以及关联流程和字段映射。 |
| [config/workflow-index.json](../config/workflow-index.json) | 安装和加载哪些流程，以及所属财务、假勤、资产、业务、人事分类。 |
| [config/workflow-versions.json](../config/workflow-versions.json) | 本企业固定目录页面、目录协议版本，以及本地每个流程支持的规则版本。 |
| `config/workflows/<类别>/<流程键>.json` | 每个流程的目标表单和流程编码、字段、选项、默认值、公式约定、资料来源、查询范围及可用状态。 |
| `workflows/<类别>/<流程名>.cjs` | 办理步骤、计算、字段组装与流程特有校验。 |
| `skills/<类别>/<流程名>/SKILL.md` | Agent 如何识别需求、收集材料、提供建议、补问和请求员工确认。 |
| `shared/`、`scripts/lib/` | 共用业务工具、官方身份适配、查询和提交边界、目录检查、个人偏好及草稿管理。 |

例如，名片流程由[配置](../config/workflows/business/business_card.json)、[实现](../workflows/business/business-card.cjs)和[Skill](../skills/business/business-card/SKILL.md)共同组成。流程键使用下划线，代码和 Skill 目录名使用连字符；加载关系见 [policy.cjs](../scripts/lib/policy.cjs)。

正式、Demo 和 Moka 是逻辑分组，不是额外的文件夹。当前实现用流程配置的 `group` 和 `availability` 判断分组及是否可发起；Moka 是 Fargo 的迁移安排，其他企业应按自己的实际系统重新设计，不能只把迁移状态改成可发起。

## 推荐从一个简单流程开始

1. **建立自己的维护副本。** 可以 Fork 公开仓库；公司的实际配置、个人资料和运行数据应放在有适当访问权限的位置。维护变更记录，避免直接修改员工已安装的版本目录。
2. **选一个规则清楚、风险较低的流程。** 例如从名片申请的结构入手，先在本企业测试应用中建立表单、审批和必要资料来源。它仍有公司模板和 HR 联系人的依赖，需要逐项替换。
3. **对照原生页面梳理规则。** 记录字段 ID、组件类型、选项值、必填条件、默认值、隐藏字段、公式、关联过滤和附件用途。业务规则可能来自页面 JS、公式及提交校验；不能假定通过 API 提交时网页交互一定会执行。
4. **同步配置、代码与 Skill。** 修改目标、字段和固定来源，同时修改办理与计算代码；Skill 说明也必须与本公司的规则一致。只注册已适配并验证的流程，在线目录和本地规则版本同步维护。
5. **用普通员工身份验收。** 覆盖正常申请、缺少资料、无权限、草稿编辑、24小时来源复用、主动刷新差异和结果回查；确认平台最终字段、金额、附件及审批路径正确，再交付员工。

不要从修改几个企业 ID 或表单 ID 开始就推断适配完成。部分 Demo 和共用模块仍带有 Fargo 的字段或规则假设，应搜索相关旧 ID、人员例外和币种约定，逐项确认是否继续适用。

## 保留身份和数据来源约束

登录、账号选择和平台访问继续使用官方 OpenYida；本包绑定当前官方账号及企业，不接收员工任意指定的提交身份。官方版本适配、连接器返回结构和字段最小范围见[连接器说明](CONNECTORS.md)。

替换资料源时，除改地址和字段，还要核对共用工具所要求的返回结构、人员身份、关联关系及错误处理。例如花名册必须匹配本次允许查询的人，汇率必须明确原币、目标币和数值，科目必须与类别合法配对。接口结构不同，应编写相应适配，不能把缺失资料交给 Agent 猜测。

财务计算需对齐原页面公式分支、舍入、换算方向和精度，页面与口述编辑复用同一计算代码。汇率和科目只取本企业固定来源；首个可核对草稿起24小时复用，编辑不续期、提交不全量联网重查，主动刷新或过期时再取并展示差异。公司应确认这一有效期内来源不自动更新的约定。明细顺序见[财务编排](FINANCE-DETAILS.md)，附件见[原生附件](ATTACHMENTS.md)。

平台权限和连接器下游权限也要单独验收。本地查询名单与校验有助于减少误用，但不能代替接收端授权；不要通过放宽资料权限、使用管理员身份或换入口来掩盖适配问题。

## 建立本企业的版本目录

本版依赖公司自定义页面作为在线目录，当前公包**未附该页面源码或部署模板**。其他企业需要另行建立、发布符合协议的页面，并把其固定页面 ID 配入 `workflow-versions.json`。不能继续引用 Fargo 的目录，也不能删除目录检查来完成安装。

协议实现以 [workflow-directory.cjs](../scripts/lib/workflow-directory.cjs) 为准，关键约定是：

- 官方 `get-schema` 返回的页面状态必须为 `ONLINE`，并包含唯一的 `YidaCodeCanvas.props.code`。
- 代码中有且仅有一对 `/* FARGOWORK_DIRECTORY_V1_BEGIN */`、`/* FARGOWORK_DIRECTORY_V1_END */` 标记，中间是合法 JSON；客户端只解析数据，不执行页面代码。
- 顶层声明 `schemaVersion`、`corpId`、`appType`、`catalogRevision`、`publishedAt`、`packageSnapshotVersion` 和 `records`；公司与应用必须匹配本地配置。
- 每条记录声明唯一的 `key`、`name`、`category`、`group`、`status`、`ruleVersion`、`minimumClientVersion`，本地已知流程的分类及分组必须一致。
- 规则版、客户端版分开管理；最低版本不跟新版自动提升，兼容小更新只提醒。首次核对或刷新时规则主版不匹配、客户端低于最低要求、流程不可用或目录无法读取，保留草稿并暂停依赖办理；有效草稿复用已有目录快照。

用普通员工账号运行 `node scripts/fargowork.cjs directory`，验证机器能读取完整目录；管理员可读或网页能打开不能代替这项验证。具体行为见[流程目录与版本核对](WORKFLOW-DIRECTORY.md)。

公开更新提示默认指向 FargoWork 的固定 GitHub 仓库，只接收稳定版本号，不下载代码。派生企业发行版应由维护者同步适配 `scripts/lib/update-notice.cjs` 的固定发布来源及链接，再测试两次超时、缓存和失败跳过；不要给员工业务输入开放任意更新地址。

## 重新验证并交付完整包

修改后的企业版本需要独立的版本号和发布记录，同时对齐 `package.json`、`package-lock.json`、在线目录与完整安装包。个人偏好通过独立入口管理，不把公司规则放入个人记忆，见[个性化说明](PERSONAL.md)。

安装器按[文件清单](../manifest.json)校验文件大小和 SHA-256，并在 [setup.cjs](../scripts/setup.cjs) 中限定必需文件。配置、说明或代码改动后，都应重新生成完整清单；增删模块时，还需同步安装器的文件约定及发布检查。清单用于完整性核对，不等同于发行者身份的数字签名。

当前公包**未附构建打包工具及完整开发测试集**，因此还不是可以一键生成其他企业发行版的模板。维护者需要补齐自己的打包和验收流程，或联系项目维护者协助；不要删除摘要检查、复用旧清单或向员工分发零散覆盖文件。

交付前至少确认：隔离安装成功、目录可读、普通员工权限正确、所选流程端到端结果正确、异常时停止提交、升级后个人偏好保留；包内不含登录凭据、真实业务材料、草稿或个人记忆。提交结果不明时先回查，不重复发起。
